# 修改、Git 同步与 NAS 发布流程

适用项目：英语剪贴本。GitHub 保存源码历史；NAS 提供正式服务；用户数据单独备份。

## 1. 确认版本与保存现场

- 查看 `git status --short`、当前分支和最近提交，确认没有其他设备或 Hermes 尚未合并的修改。
- 有网络时先获取远端状态；只做快进更新，出现分叉先比较并合并，禁止强制覆盖。
- 首次接手或 NAS 被直接修改后，比较 NAS 的源码副本、实际运行程序与 Git 版本。不能把旧 Git 代码直接覆盖到线上。
- 项目修改前备份放 `work/backups/<日期>-<任务>/`，保持原相对路径并加 `.before`；README 记录原因、时间和原提交/发布版本。
- 较大功能在独立任务分支开发。不要同时让两端修改同一批文件。

## 2. 修改与验证

依赖首次安装或锁文件变化时：

```sh
npm ci --ignore-scripts --no-audit --no-fund
```

普通前端修改使用已有词包构建，避免在每次发布时重建词库：

```sh
npm run lint
npm run build:web
node --check nas/server.mjs
node --check nas/import.mjs
```

- `npm run build` 会触发 `prebuild` 重新生成图标和词库；仅在明确需要更新这些资源时使用。
- 前端改动在本地浏览器检查受影响流程，包括手机布局；记录、编辑、筛选等操作只用测试数据。
- 同步或后端改动使用独立的 `EC_DATA_DIR`、`EC_WEB_DIR` 和空闲端口，禁止指向正式数据目录。
- `scripts/smoke-test.mjs` 是原有 macOS Chrome 脚本；未在当前系统实际运行就不能记为通过。
- 有失败或未覆盖项，应修复或明确记录原因；不得把未验证写成已通过。

## 3. 提交并同步 GitHub

- 审查 `git diff` 和待提交文件，确认只有本任务内容。
- 源码、锁文件、通用配置模板和相关文档一起提交；实际环境文件、用户词条、账号信息、密钥、导出、日志、依赖、构建产物和备份不进 Git。
- 每次完成修改生成有意义的提交，并推送相应分支；推送后核对 GitHub 分支的提交编号。
- 分支合入后，以待发布分支的确切提交构建。不得使用 `--force`、`reset --hard` 或清理掉未知改动。
- 无法认证或推送失败时，保留本地提交，并明确报告“已提交但未同步”。

## 4. NAS 发布（仅在任务包含发布时）

- 先确认 NAS 没有他人正在发布，比较实际运行文件与已知基线。
- 从干净且已同步的提交制作程序包，只包含所需前端产物、后端及启动文件，附文件清单和 SHA-256。
- 使用唯一发布名，例如 `release-20261026-<提交短编号>`；在新目录完成准备，不直接覆盖唯一运行副本。
- 记录旧程序、端口、配置引用及启动/守护方式。配置文件和数据不混入程序包。
- 切换前取得一致的数据备份。当前 JSON 后端在内存维护数据：涉及数据回退或导入时必须停写，防止内存旧副本覆盖磁盘。
- 切换后验证公共健康检查、前端资源，以及本次改动涉及的登录后读写/同步流程。只看到健康检查成功，不能代表全部验收完成。
- 失败时恢复旧程序；程序回退不得覆盖用户数据。涉及数据结构变化时，另行核对兼容性及发布后的新增数据。
- 不自动删除旧版本、备份或用户文件。

发布记录保存为 `docs/releases/<发布名>.md`，包括提交编号、实际发布时间、程序清单校验值、旧版本、备份位置、验收结果及回退操作。只记录路径及结论，不记录凭据或用户内容。

## 5. 每次交付的说明

说明四项：本次变化；实际验证结果和未完成项；Git 提交及推送状态；NAS 是否发布及对应版本。
